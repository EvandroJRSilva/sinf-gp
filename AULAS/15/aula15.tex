\begin{frame}{Gerenciamento de configuração}
	\begin{itemize}
		\justifying
		\item<1-5> Os softwares \textbf{mudam constantemente} durante seu desenvolvimento e uso
		\begin{itemize}
			\justifying
			\item<2-5> Defeitos são descobertos.
			\item<3-5> Requisitos mudam.
			\item<4-5> Novas versões de hardware e software.
			\item<5> Concorrentes lançam novidades.
		\end{itemize}
		\item<6> À medida em que são feitas alterações no software, uma nova versão de um sistema é criado. A \textbf{maioria dos sistemas}, portanto, pode ser encarada como um \textbf{conjunto de versões}, \textbf{cada uma} delas tendo que ser \textbf{mantida e gerenciada}.
	\end{itemize}
\end{frame}

\begin{frame}{Gerenciamento de configuração}
	\begin{itemize}
		\justifying
		\item O gerenciamento de configuração
		\begin{itemize}
			\justifying
			\item<1-> Está relacionado às \textbf{políticas}, aos \textbf{processos} e às \textbf{ferramentas} para o gerenciamento de sistemas de software que mudam.
			\item<2-> É \textbf{útil} para \textbf{projetos individuais}, pois é fácil para uma pessoa esquecer quais alterações foram feitas.
			\item<3> É \textbf{essencial} para \textbf{projetos em equipe}, nos quais vários desenvolvedores trabalham em um sistema de software ao mesmo tempo.
		\end{itemize}
	\end{itemize}
\end{frame}

\begin{frame}{Gerenciamento de configuração}
	\begin{itemize}
		\justifying
		\item Quatro atividades principais
		\begin{enumerate}
			\justifying
			\item<1> \textbf{Controle de versão}: envolve manter o controle das várias versões dos componentes do sistema e garantir que as mudanças feitas em componentes por diferentes desenvolvedores não interfiram umas com as outras.
			\item<2> \textbf{Construção de sistema}: processo de reunir componentes, dados e bibliotecas do programa, compilando-os e ligando-os para criar um sistema executável.
			\item<3> \textbf{Gerenciamento de mudanças}: envolve manter o controle das solicita-ções de mudança de clientes e desenvolvedores no software já entregue, elaborar os custos e o impacto de fazer essas mudanças e decidir se e quando as alterações devem ser implementadas.
			\item<4> \textbf{Gerenciamento de lançamentos} (\textit{releases}): envolve a preparação de software para o lançamento externo e o acompanhamento das versões de sistema que foram lançadas para uso do cliente.
		\end{enumerate}
	\end{itemize}
\end{frame}

\section{Gerenciamento de versões}

\begin{frame}{Gerenciamento de versões}
	\begin{itemize}
		\justifying
		\item O que é controle de versão? Onde vive? O que faz? Do que se alimenta?
		\begin{itemize}
			\justifying
			\item<2-> É um \textbf{sistema} que \textbf{armazena modificações} em um arquivo ou conjunto de arquivos em função do tempo, e \textbf{permite o acesso a versões específicas a qualquer momento}.
			\item<3> Em nosso contexto usamos para versionar códigos-fonte, mas um controle de versionamento pode ser aplicado sobre praticamente qualquer tipo de arquivo.
		\end{itemize}
	\end{itemize}
\end{frame}

\begin{frame}{Gerenciamento de versões}
	\begin{itemize}
		\justifying
		\item Com um \textbf{Sistema de Controle de Versionamento} (VCS) é possível
		\begin{itemize}
			\justifying
			\item<2-> Voltar ao estado anterior dos arquivos selecionados;
			\item<3-> Voltar ao estado anterior de todo o projeto;
			\item<4-> Comparar diferentes modificações;
			\item<5-> Caguetar a pessoa que fez uma modificação que está causando erro;
			\item<6-> Saber quem adicionou alguma nota (sobre problema ou sugestão), onde e quando;
			\item<7-> Se você sem querer apagou tudo, com um VCS é maior a probabilidade de você conseguir recuperar o que perdeu;
			\item<8> Tudo isso sem muito custo computacional.
		\end{itemize}
	\end{itemize}
\end{frame}

\section{Gerenciamento de lançamentos}

\begin{frame}{Gerenciamento de lançamentos}
	\begin{itemize}
		\justifying
		\item Um lançamento (\textit{release}) de sistema é \textbf{uma versão} do sistema de software distribuída para os clientes.
		\item Em alguns casos é possível identificar 2 tipos de lançamentos:
		\begin{itemize}
			\justifying
			\item \textit{\textbf{Major releases}}: em alguns casos referidos como \textbf{LTS} (\textit{Long Term Service}), os quais oferecem novas funcionalidades significativas. Costuma ser pago.
			\item \textit{\textbf{Minor releases}}: que consertam defeitos e solucionam problemas relatados por clientes. Costuma ser gratuito.
		\end{itemize}
	\end{itemize}
\end{frame}

\begin{frame}{Gerenciamento de lançamentos}
	\begin{itemize}
		\justifying
		\item Um lançamento de produto de software não é apenas o código executável do sistema. O lançamento também pode incluir:
		\begin{itemize}
			\justifying
			\item<2-> \textbf{Arquivos de configuração}, que definem como o lançamento deve ser configurado para instalações específicas.
			\item<3-> \textbf{Arquivos de dados}, como arquivos de mensagens de erro em diferentes idiomas, que são necessários para a operação bem-sucedida do sistema.
			\item<4-> \textbf{Programa de instalação}, que é usado para ajudar a instalar o sistema no hardware de destino.
			\item<5-> \textbf{Documentação}, eletrônica e em papel, que descreva o sistema.
			\item<6> \textbf{Embalagens e publicidade associada}, que foram concebidas para esse lançamento.
		\end{itemize}
	\end{itemize}
\end{frame}

\subsection{Marketing}

\begin{frame}{Marketing}
	\begin{itemize}
		\justifying
		\item Além do trabalho técnico envolvido na criação de uma distribuição do lançamento, é preciso preparar \textbf{material de propaganda e publicidade}
		\begin{itemize}
			\justifying
			\item<2-> Pode ser necessário conceber estratégias de marketing para convencer os clientes a comprarem o novo lançamento do sistema.
			\item<3-> É preciso pensar muito no momento dos lançamentos:
			\begin{itemize}
				\justifying
				\item<4> Se eles forem \textbf{frequentes demais} ou exigirem \textbf{atualizações de hardware}, os clientes podem não passar para o novo lançamento, especialmente se tiverem que pagar por ele.
				\item<4> Se os lançamentos do sistema forem \textbf{pouco frequentes}, a participação de mercado pode diminuir à medida que os clientes mudarem para sistemas alternativos.
			\end{itemize}
		\end{itemize}
	\end{itemize}
\end{frame}

\subsection{Criação do lançamento}

\begin{frame}{Criação do lançamento}
	\begin{itemize}
		\justifying
		\item É o \textbf{processo de criar o conjunto de arquivos e documentação} que inclui todos os componentes do lançamento do sistema. Esse processo envolve várias etapas, destacadas a seguir:
		\begin{enumerate}
			\justifying
			\item<2> O \textbf{código executável} dos programas e todos os arquivos de dados associados devem ser identificados no sistema de controle de versão e marcados com o identificador de lançamento.
			\item<3> \textbf{Descrições de configuração} podem ter de ser escritas para diferentes sistemas operacionais e de hardware.
			\item<4> \textbf{Instruções atualizadas} podem ter de ser escritas para os clientes que precisam configurar seus próprios sistemas.
			\item<5> \textbf{Scripts} para o programa \textbf{de instalação} podem ter de ser escritos.
			\item<6> \textbf{Páginas da web} precisam ser criadas descrevendo o lançamento, \textbf{com links} para a \textbf{documentação} do sistema.
			\item<7> Finalmente, quando todas as informações estão disponíveis, uma \textbf{imagem mestre executável} do software deve ser preparada e entregue para distribuição a clientes ou para revendas.
		\end{enumerate}
	\end{itemize}
\end{frame}

\subsection{Documentação}

\begin{frame}{Documentação}
	\begin{itemize}
		\justifying
		\item Para documentar um lançamento
		\begin{itemize}
			\justifying
			\item<1> Devem ser registradas as \textbf{versões específicas dos componentes do código-fonte} que foram utilizadas para criar o código executável.
			\item<2> É necessário \textbf{manter cópias} dos arquivos \textbf{do código-fonte}, \textbf{dos executáveis} correspondentes e de todos os \textbf{arquivos de dados e configurações}.
			\item<3> Pode ser necessário manter \textbf{cópias} dos \textbf{sistemas operacionais mais antigos} e de outro software de apoio porque eles ainda podem estar em operação (Docker e/ou máquina virtual).
			\item<4> \textbf{Registrar} as \textbf{versões do sistema operacional}, as \textbf{bibliotecas}, os \textbf{compiladores} e \textbf{outras ferramentas} utilizadas para construir o software.
		\end{itemize}
	\end{itemize}
\end{frame}

\subsection{Instalação}

\begin{frame}{Instalação}
	\begin{itemize}
		\justifying
		\item Quando se planeja a instalação de novos lançamentos do sistema, não se deve assumir que os clientes sempre instalarão esses novos lançamentos.
		\begin{itemize}
			\justifying
			\item Alguns usuários podem estar felizes com um sistema atual e podem não considerar justificável absorver  o custo de mudar para um novo lançamento.
			\item Os novos lançamentos do sistema, portanto, não podem se basear na instalação dos lançamentos prévios.
			\item Opção viável: \textbf{SaaS}.
		\end{itemize}
	\end{itemize}
\end{frame}

\section{Atividade}

\begin{frame}{Atividade}
    \begin{itemize}
        \justifying
        \item Iniciar o gerenciamento de configuração
        	\begin{itemize}
        		\justifying
        		\item Escolher e justificar o uso de um VCS distribuído.
        		\item Criar o repositório e fazer os \textit{commits} (todos do grupo, não necessariamente somente commits com código).
        		\item Testar o software da outra equipe, e na aba de \textit{Issues} (ou equivalente do VCS escolhido):
        			\begin{itemize}
        				\item Sugerir alterações (tenham bom senso).
        				\item Reportar bugs.
        			\end{itemize}
        		\item Implementar as alterações que façam sentido, e consertar os bugs.
        		\item Registrar as mudanças (\texttt{changelog} ou equivalente).
        	\end{itemize}
        \item Ter, pelo menos, 2 \textit{releases} (1 \textit{major} e 1 \textit{minor}) do sistema --- não necessariamente um instalável, ou código fonte.
    \end{itemize}
\end{frame}
